# 全量系统深度测试工程 — 设计文档

> 状态：设计已获用户逐节确认（2026-07-10）。下一步 → writing-plans 出实施计划。

## 目标

对 WechatAgent 整个系统做一次**可上线级别、比真人还严谨**的全量功能与体验走查：从前端真实点击逐页验收 UI/功能，串到后端运营逻辑、数据库落库、外部依赖，系统性发现并结构化记录所有问题（含"不好用/看不懂/不友好/慢"这类体验问题），产出一份可从发现一直用到修复收口的统一台账。

**验收标准**：模仿一个首次使用的真实用户，操作不方便、不理解、不友好、卡顿延迟的地方全部记录在册。不只是"功能对不对"（QA），还要"好不好用、快不快"（UX + 性能）。

**本工程只发现+记录，不修复**。修复是台账定稿、用户定优先级后的独立阶段。

- **真实发送测试联系人**：**吴界**（`wxid_ydzaomn4scsb12`，账号 102）+ **AI应用开发**（账号 102 好友）——两个都用于真实发送端到端闭环验证。

## 第 1 节：发送红线护栏（生产环境安全边界）

生产上任何"真发给真人客户"都是不可接受的事故。三道护栏，测试前建、测试后拆。

**第 1 道 · 测试开始前置（一次性）**
- 盘点账号 102 当前所有 `managed` 联系人，快照记录原状（存台账头部，供收尾恢复）。
- 除**吴界 + AI应用开发**外，全部临时改回 `normal`（normal 只持久化不回复，webhook 灌消息不触发发送）。
- 走查开始前确认吴界/AI应用开发两个联系人为 managed 且身份正确。

**第 2 道 · 走查中的分类护栏**
- **只读/UI 类**（看页面、加载数据、打开表单弹窗但不提交）→ 自由跑，零风险。
- **写库类**（CRUD、审核、发布、配置保存）→ 可放手做（无真实数据顾虑），收尾清理。
- **真实发送类**（webhook 灌消息、campaign dispatch、cockpit 手动发送、名片推送）→ **只允许指向吴界 / AI应用开发**。campaign 圈人时严格校验受众只含这两人才 dispatch，否则只验证到"预览/圈人"为止。

**第 3 道 · 收尾恢复（一次性）**
- 删除走查期间造的测试数据。
- 按第 1 道快照恢复联系人状态（临时改 normal 的恢复原状）。
- 台账留"环境变更与恢复"记录，确保生产状态零残留。

## 第 2 节：五维验收清单

每个页面/功能过五个维度。L1/L2/L3 是"对不对"，UX/P 是"好不好用、快不快"。

**L1 · 技术健康（每个页面/子视图必过）**
- 能打开、不白屏、不卡死；console 无 error（warn 记录不算 fail）
- 首屏数据 API 无 ≥400；SSE/WebSocket 页面连接正常
- 主要动作能唤出（表单展开、弹窗/向导/抽屉能打开）
- 空态/加载态/错误态三态都验

**L2 · 功能正确（对核心动作真实操作，验到后端 + 数据库）**
- 动作真执行：CRUD 真写真改真删、审核/发布/启停/激活/回滚真生效
- 后端状态核对：操作后查对应 API 返回值
- **数据库落库核对**：直连 117 MongoDB 查文档，字段/状态/关联对不对
- 关键链路端到端：webhook→决策→审查→outbox→真发（吴界/AI应用开发）、知识导入→审核→召回、campaign 圈人→派发、请示通道触发→收件箱→裁决

**L3 · 业务正确性抽验（真 LLM 决策质量，代表性场景）**
- 对话话术质量、画像/标签合理性、知识召回准确性、请示通道判断——真模型跑、人读日志判断
- 波动大不追全覆盖；生产 LLM 端点只 2 并发线程，**严格串行不并发**

**UX 审计维度（贯穿 L1/L2，"比真人严谨"的落点）** — 扮演首次使用的真实用户，每页记录：
- **看不看得懂**：文案有无黑话/英文裸词/canonical id 直显
- **绕不绕**：完成任务几步、有无多余跳转、关键动作藏不藏
- **反馈友不友好**：报错是否技术栈原文、成功有无明确反馈、危险动作有无二次确认
- **空态引导**：空白页有无告诉用户下一步
- **一致性**：同类动作在不同页面位置/措辞是否一致
- **认知负担**：一屏信息是否过载、层级是否清晰
- 每条 UX finding 附一句**首次使用者的真实感受旁白**

**P · 前端性能与响应感受（贯穿每个页面）**
- 客观指标（playwright 采集）：首屏加载耗时、每个 `/api` 响应时间（>1s 记录/>3s 标 High）、大数据量渲染（通讯录 4832 好友/知识树/图谱滚动卡顿）、交互响应延迟（点了没反应的空窗）、首屏 bundle 体积 + 该压没压的大响应
- 主观感受：等待会不会让人以为坏了、有无 loading 兜底、慢是偶发还是稳定
- 严重度按"用户能不能忍"：>3s 无 loading 的核心页=High，1-3s=Medium，有 loading 兜底的慢=Low

## 第 3 节：问题台账结构

**台账位置**：`docs/superpowers/specs/2026-07-10-full-system-test-findings.md`（单文件，按频道分节累积，从发现一直用到修复收口）。

**台账头部**：
- 环境变更记录（哪些联系人改了 normal、造了哪些测试数据）→ 供收尾恢复
- 覆盖矩阵（19 频道 × L1/L2/L3/UX/P × 状态）→ 一眼看进度，断点续跑依据
- 已知边界清单（见第 5 节）
- 红线预期清单（走查前列出，对照防误报）

**每条 finding 字段**：
```
### [F-序号] 一句话标题
- 频道/页面：如 userOps → cockpit → 画像分析
- 类型：功能bug / UX问题 / 数据一致性 / 性能 / 红线违规
- 严重度：Critical(阻断/白屏/链路断/红线) / High(核心功能错/数据错) / Medium(次要功能/明显不友好) / Low(体验瑕疵/文案)
- 层级：L1 / L2 / L3 / UX / P
- 影响范围：单页面 / 多页面列表 / 全局模式（同根因聚合）
- 优先级：P0/P1/P2（仅在严重度与该不该先修不一致时点出，如 Low 但高频）
- 复现步骤：1.2.3. 精确到点哪个按钮、填什么
- 现象：实际看到什么（截图路径 + console/API 错误原文 + DB 查询结果摘要）
- 预期：应该是什么
- 初步根因：读代码后的判断(file:line)，或"待定位"
- 验证状态：CONFIRMED(亲验复现) / SUSPECTED(疑似需确认)
- 状态：Open / Fixing / Fixed / Verified / WontFix-红线预期 / Duplicate
- 修复建议：一句话方向，不含实现
```

**关键纪律**：
- **红线预期 vs 真 bug 区分**：`blocked_unverified_product_claim`（空KB 拦报价）、`held_by_ai_policy`、auto-verify 自动 reject、请示通道拦截等是红线正确行为，标 `WontFix-红线预期` 不误报。
- **CONFIRMED/SUSPECTED 分级**：亲验复现才 CONFIRMED；LLM 单次波动、截图没看真切标 SUSPECTED。
- **同根因聚合**：同一根因在多页面表现，记 1 条主 finding + 影响范围列全部受影响页面，不记 N 条。

**证据资产归档**：
- 截图存 `screenshots-fulltest/<频道>/<F序号>-<步骤>.png`
- DB 查询：贴 mongosh 查询语句 + 结果摘要（不贴大 body）
- API 错误：贴请求路径 + 状态码 + 响应体关键字段

## 第 4 节：subagent 编排与执行批次

**核心约束**：① 生产 LLM 端点只 2 并发线程（超了 tool_use 劫持/失败）；② playwright 打 117 单台真实 Chrome，多 agent 同时驱动会抢浏览器/焦点。编排必须尊重这两条。

**分工模型**：主控（我）持台账/覆盖矩阵/护栏状态，做批次调度 + findings 汇总去重；每个 subagent 领一个频道（大频道拆子批），完成 L1+L2+UX+P 全维度走查，产出结构化 findings 回收合并。subagent 全部 `model: opus`（CLAUDE.md 红线）。

**并发策略**：
- **L1/L2/UX/P（不打真 LLM）**：瓶颈是单台 Chrome → **串行为主**，一次一个 subagent 驱动浏览器走一个频道（状态干净、截图不串、findings 不撞车）。
- **任何触发真 LLM 的动作（不限批 4/L3）**：如 systemStrategy 的 AI 生成 profile、knowledge 的 AI 问答/校验、command-center 指令执行等，**严格串行、绝不并发**，单路跑。这条约束跨批次生效，不是只在批 4。
- 整体串行流水：一个频道走完 → findings 回收 → 下一个。慢功出细活。

**执行批次（依赖排序）**：
- **批 0 · 护栏与地基**：建发送护栏（盘点 managed、除吴界/AI应用开发外改 normal、快照）→ 确认 playwright 登录 117 → health + worker-health + MCP 探针确认后端/依赖活着 → 建台账骨架 + 覆盖矩阵。
- **批 1 · 系统/配置频道**（低风险只读多）：llmProviders、systemStrategy、askHumanConfig、operations、autonomy、evolution、quality、sendAnalytics。
- **批 2 · 知识组**（最复杂、纯内部闭环无真发风险）：content、referralCards、knowledgeWiki（拆 workbench/library/console 三子批）。
- **批 3 · 运营组只读+CRUD**：command、accountManagement、overview、userOps（smart/roster/traditional 三模式）、productsDeals、askHuman、campaign（只到圈人/预览）。
- **批 4 · 真实发送闭环**（护栏下，只指向吴界/AI应用开发）：webhook 灌消息→决策→审查→outbox→真发、campaign 对测试联系人 dispatch、cockpit 手动发送、名片推送；L3 真 LLM 抽验也在这批串行跑。
- **批 5 · 收尾**：删测试数据、按快照恢复联系人状态、台账补覆盖矩阵终态 + 环境恢复确认 + 已知盲区清单。

**断点续跑**：覆盖矩阵 + 台账落盘即进度，某批中断从矩阵未完项接着跑（会话可能压缩，必要）。

## 第 5 节：执行纪律与已知边界

**纪律 1 · 引用必亲验，根因不猜**：台账里"初步根因 file:line"当场 Read/Grep 亲验，验不出标"待定位"，绝不写猜测根因（CLAUDE.md 最高红线）。"慢"要有 playwright 实测数字。

**纪律 2 · 红线预期 ≠ bug**：走查前先列"红线行为预期清单"对照，把系统做对的事标 WontFix-红线预期，不记成 bug。

**纪律 3 · 发送护栏每批复检**：批 4 每次 dispatch/发送前重新确认受众只含吴界/AI应用开发，不信任"之前改过 normal 了"的假设。

**纪律 4 · 不过拟合、不为验收改业务**：只记录问题，绝不为让页面"看起来对"改 prompt/阈值/guards。修复是独立阶段。

**已知边界（诚实写进台账头部）**：
- **视觉盲区**：通过截图+DOM"看"，像素级错位/颜色对比/字体渲染可能漏，可疑处丢截图给用户人工确认。
- **网络延迟盲区**：性能测的是 117 本机环回，测不到真实用户经公网的网络延迟（公网 502 够不着）。
- **LLM 波动**：L3 单次结果可能是模型波动非真 bug，标 SUSPECTED，必要时多 seed 复验。
- **并发真实性**：串行走查，测不到"多用户/多账号同时操作"的并发问题（那类靠现有 PBT/集成测试覆盖）。
