# 上线前全量业务逻辑测试方法论 — 设计

> 状态:brainstorming 产出,待用户审阅 → writing-plans。
> 日期:2026-06-30。事实底座:47 域饱和式深读+对抗证伪审计(`deepread-verify-result-2026-06-30.json`,96 agent / 1077 万 token)。

## 1. 问题与目标

main 近期合并大量新业务(campaign / evolution / content-assets / ask-human / tag-trust / digital-twin / suspected-deals / 发送节流 / 知识修复闭环),旧的 13 域 biz-test 基线与两条旧 spec(agent-autonomy-loop / user-ops-agent-hardening,均挂 **Sunset Notice 2026-05-25**)已失准。

用户要的不是"再跑一遍测试",而是**确认全部业务逻辑按设计能跑、能上线**,且已意识到**现有测试本身不可信**。这是两件必须分开的事:

- **建尺**:重建"每个业务域按设计应有的行为 + 红线 + 入口"的权威清单——因为 spec 不可信、测试不可信,正确性的唯一来源只剩 **代码实现 + CLAUDE.md + docs/agent-policy.md 红线**。
- **量**:拿这把尺做三件校验——治假绿、找 gap、找真 bug。

## 2. 正确性的分层定义(方法论核心)

"正确"没有单一可信源,必须分层,且**拿代码当尺子量代码是循环论证**(代码即被测对象)。所以正确性来自代码之外、且分层:

| 层 | 定义 | 可判定性 | 上线把关 |
|---|---|---|---|
| **L1 红线否定式** | "绝不能 X"(无人工接管/AI永不自动verify/产品声明须背书/画像draft不自动生效/AI永不直写outcome/演化器隔离/CAS防双计) | 最硬,违反即确定 bug,无歧义 | **go/no-go 硬门** |
| **L2 设计意图正向** | 文档明文"该做什么"(状态机迁移/作息defer/去重幂等/灰度分桶) | 较硬,但需标依据+新鲜度 | 必测,允许少量观测 |
| **L3 正向质量主观** | 话术好不好/升档时机对不对 | 无机械金标 | 多采样+异族judge逼近,**责任在人** |
| **L4 孤儿行为** | 代码有实现但红线和文档都没定义对错 | **不可判定** | **逐条交用户拍板** |

L4 是最值钱的产出:它逼出一批"连设计意图都没写下来"的业务,假装"现状即正确"是不诚实的。

## 3. 已执行:饱和式审计(workflow 并行,只读)

**workflow 的正确用法**:静态只读审计天然 fan-out 适合并行(不碰生产 LLM 端点,跑在 Claude 上,不触发"端点 2 线程并发"红线);**真实 LLM 端到端执行必须串行**(端点 2 线程,并行必雪崩)。

已完成两阶段:
1. **7 锚点穷举**(路由表/后台worker/发送主链路/agent子模块/数据集合/红线守卫/新增业务)→ 370 条能力,交叉合并去重 → **47 业务域全集**(`audit-2026-06-30-anchors.json` + `biz-domains-2026-06-30.json`)。
2. **47 域 × (深读 + 对抗证伪)**:每域一 agent 从代码派生"设计行为/红线/现有测试可信度/真缺口/孤儿",再一独立 agent grep 实证、专门推翻夸大结论。≤5 并发分批 + 每 agent 3 次重试容错。产出 `deepread-verify-result-2026-06-30.json`。

对抗证伪生效证据:共推翻 ~70 条夸大结论(如 J2 推翻"check-skip-ledger.sh 是孤儿"——实为 nightly skip-gate 活守门;guards 推翻 4 条)。单向证实会漏,双向验证更可靠。

## 4. 审计结论:测试矩阵(事实底座)

**全局画像**:47 域 = P0 红线 38 + P1 闭环 9。测试可信度:可信 2 / 可信(有缺口) 25 / **假绿 12 / 缺失 8**。即 **20 个域的测试现状不可上线信赖**——印证"测试已失准"。验证过的真缺口 **300 条**,孤儿行为 **190 条**。

### 4.1 最高危:16 个 P0 红线域 假绿/缺失(上线前必处理)

**假绿 10**:digital-twin关系类型建议 / 知识对话工作台 / 知识长任务worker群 / 管理Agent / guide引导 / 账号管理 / 联系人管理 / LLM provider热切换 / 多租户隔离 / 红线CI lint。

**缺失 6**:去抖聚合调度 / Shadow模拟 / campaign营销活动 / 评测体系 / 鉴权 / 死代码识别。

### 4.2 假绿的典型手法(审计实证,反面教材)

- **平行实现自证**:多租户隔离 / Follow-up worker / domain版本灰度 / referral 的隔离测试,**在测试体内自己重抄一遍 Mongo filter** 去查库断言跨租户为空——验的是"MongoDB 按 workspace_id 会过滤"(恒真,等于测 Mongo 本身),而非"handler 真把 current_workspace 注入了 filter"。生产 filter 改了测试不会红。
- **循环论证**:管理Agent dry_run_isolation 手工插一条 dry_run 记录,断言业务集合 count==0——但集合本来就空(从未调真 handler)。
- **状态码即成功**:LLM provider activate 只断言 HTTP 200,从不发后续 LLM 调用证明 registry 真换了 provider,也不查 DB 恰一条 isActive=true。
- **空壳 #[ignore]**:Follow-up worker_reclaim 只 insert+find 回读断言 status=="running"(任务没被碰过),从不调 reclaim/tick;guards revision_recheck_action_gate 是空函数体骨架。

## 5. 上线前测试执行方案(待 writing-plans 细化)

四阶段流水线,**静态并行 + 真实串行**:

1. **建尺(已完成)**:47 域权威行为清单 + 测试矩阵。
2. **治假绿(P0 优先)**:12 假绿域 + 8 缺失域逐一重写/新建测试,断言**实质行为而非平行实现/状态码/空壳**。原则:测 handler 真接线(注入 workspace_id 真生效)、测红线真拦(坏签名真 400、activate 真换 registry)。
3. **真实串行执行**:按 P0→P1 优先级,在 server 117 真 LLM 跑端到端业务测试(扩充 biz-test);**严守串行**(端点 2 线程);端点失败标 BLOCKED 不假绿。
4. **孤儿行为定夺**:190 条孤儿逐批交用户拍板"正确该是什么",再决定测或不测。

**红线(贯穿全程)**:不过拟合(绝不为过测试改业务逻辑/prompt/guards/阈值);改 src 前确认普适性+取舍问用户;agent-first(语义判断交 LLM,机器只做确定性度量);新增测试只增量 append 不删旧维度;基线 lib≥350 + 4PBT≥33 不回归。

## 6. 范围与边界

- **不在本轮**:Group/Moments 运营域(Phase 1 范围外);真去修 300 条缺口里需改 src 的项(那是独立工程,改前逐项问用户)。
