## 2. “100% 阅读”的完成定义

每个基线文件必须在 `file-ledger.csv` 中恰好出现一次，并满足以下一种状态：

1. `read_complete`：文本内容从头到尾亲读，已记录子系统、职责、调用关系、数据读写、业务规则、失败行为及证据锚点。
2. `verified_non_text`：确认为二进制、锁文件、测试密钥或大体积 fixture，已记录用途、消费者及不逐字读取的理由，并通过引用点或格式工具核验系统角色。

只看符号、搜索结果、文件头、局部片段、测试名称或旧审计报告均不算完成。文件哈希变化后未重读也不算完成。

## 3. 审查范围

### 3.1 全文阅读

- Rust：`src/**/*.rs`、`tests/**/*.rs`、迁移、模型、路由、Worker 与 Agent。
- 前端：`frontend/src/**/*.{ts,tsx,css}`、构建配置、契约 fixture。
- 自动化：`scripts/**/*.{sh,ps1,py,js,mjs,cjs}`、CI 与部署脚本。
- 配置规范：Cargo/NPM/Vite/TypeScript 配置、`.env.example`、`.kiro/specs/**`、项目规则。
- 产品与架构文档、正式设计、历史计划和审计记录；历史材料只作为意图与演进证据。
- 网站源码与静态页面文本。

### 3.2 结构核验

- PNG/SVG：核验路径、尺寸、引用者、用途，必要时视觉检查。
- 测试 PEM：只核验测试用途和引用范围，不复制密钥。
- Base64 fixture：核验 MIME、大小和消费者，不复制完整编码。
- `Cargo.lock`：核验锁定状态、依赖图和风险依赖，不逐字符解释校验和。
- Proptest regression fixture：核验失败种子及对应测试。

### 3.3 不纳入基线覆盖率

- `.git/`、`target/`、`node_modules/`、日志、PID、临时文件、压缩包和编译产物。
- 未跟踪的本地探针、截图、备份及 `.env`。
- 本次新增的 `docs/system-review/**`。

排除不等于忽略风险：秘密、部署产物和未跟踪资产另做存在性与来源检查，但不读取或记录真实秘密值。

## 4. 证据与确定性规则

事实至少绑定一种当前证据：代码定义与调用点、数据模型与真实过滤条件、路由注册与处理器、配置与启动接线、测试断言及生产实现、规范与实现差异。

结论统一标记：

- `FACT`：当前代码直接证明。
- `CONTRACT`：规范或测试声明，生产接线另行核实。
- `RUNTIME_UNVERIFIED`：代码存在但未通过外部环境或运行核验。
- `UNKNOWN`：证据不足，禁止猜测，进入待核实项。

严重度与事实确定性分开记录。

## 5. 分阶段计划

### 阶段 0：冻结与台账

固定提交、文件集合与 SHA-256；逐文件分类；建立变更失效检查。验收标准是基线文件集合与台账集合完全相等，无重复、无遗漏。

### 阶段 1：规则、产品意图与启动骨架

阅读项目规则、README、核心架构、Cargo/NPM/Vite/CI/环境配置，以及 `main.rs`、`lib.rs`、`config.rs`、路由总装配和数据库入口。产出进程拓扑、外部依赖与默认开关矩阵。

### 阶段 2：数据层

完整阅读 `models.rs`、数据库访问器、索引和全部迁移；建立集合目录、租户键、状态闭集、索引和迁移演进图；逐集合反查所有读写点。

### 阶段 3：外部边界

阅读 Auth、Session、JWT、Webhook、MCP、LLM、账号同步和媒体存储；建立认证授权、密钥生命周期、签名、限流、超时重试与错误映射图。

### 阶段 4：私聊 Agent 主链

按真实调用顺序阅读 Webhook 去抖、Reaction、Gateway、Knowledge Router、Decision、Review、Guards、Memory、Escalation、Outbox 与 Dispatcher；对每个 return/error/cancel/retry 分支建立状态迁移表。

### 阶段 5：管理面与业务域

阅读 Management Agent 工具、风险分类、dry-run、确认 CAS、结果核实，以及联系人、Campaign、产品成交、素材、名片、请示、策略、Taxonomy、DomainProfile 和版本发布；建立授权、作用域、副作用与审计矩阵。

### 阶段 6：知识系统

阅读导入、文档、切片、Revision、核验、引用图、Catalog、Answer Agent、Digest、Gap Signals、Feedback 和 Ingest；追踪每种来源从入库到 verified/active/召回/反馈的生命周期。

### 阶段 7：演化、规划与 Worker 舰队

阅读 Evolution cohort/proposal/replay/significance/release/rollback/runtime flag，以及 Planner、Task、Import、Cold Contact、Silence、Knowledge Task、Catalog Rebuild 等 Worker；核验启动门、claim/lease/heartbeat、幂等、多副本和恢复语义。

### 阶段 8：前端全量

从入口、Store、API 客户端和频道导航逐页阅读组件、样式与契约；将每个用户动作映射到真实后端路由和状态，识别占位、静态假数据、错误态、权限态和字段漂移。

### 阶段 9：测试、脚本、CI、部署与历史材料

阅读全部单元/PBT/集成/E2E 测试和 fixture；映射需求—实现—测试；核实 ignored、soft-fail、外部依赖；阅读脚本、CI、部署、网站和历史计划，区分现状与遗留方案。

### 阶段 10：交叉验证与报告

从入口到副作用、从集合到所有写入点、从前端动作到后端、从测试到生产实现四向反查；高风险发现独立反向核验；重算哈希；执行可承受的构建、测试和静态检查；交付架构、业务逻辑、数据字典、状态机、风险与优化顺序。

### 阶段 11：真实业务逻辑复审（100% 覆盖后的第一轮）

仅在基线文件达到 100% 阅读、阶段 10 的交叉验证完成后启动。按真实运营角色、客户旅程和生产副作用重新走查端到端业务闭环，不以模块边界、接口 200 或单测通过代替业务成立。逐条检查：入口是否可达、数据是否来自真实事实源、状态是否能继续推进、失败是否可恢复、账号/租户/对象身份是否贯穿、人工确认看到的对象是否就是实际执行对象、指标是否能支持业务判断。

本轮内部采用循环审查：提出候选 → 沿生产调用链正向证明 → 从数据写入和最终副作用反向证明 → 搜索反证与既有保护 → 复现或最小验证 → 与 `findings.md` 去重。无法闭合可达性、影响或证据的候选降为 `UNKNOWN`/观察项，不进入人类确认清单。

### 阶段 12：业务简化与反过度工程复审（第二轮）

在第一轮结论稳定后，从“能否用更少概念、更短链路、更少状态和更明确的单一事实源完成同一业务目标”重新审查全系统。重点识别重复入口、平行状态机、重复配置、无消费者抽象、只增加维护成本的版本/审批层、可由现有能力闭环却另建子系统的设计，以及复杂度掩盖真实失败语义的路径。

本轮同样循环执行：提出简化候选 → 证明当前复杂度的真实成本 → 搜索其必要性和已有消费者 → 比较最小可行替代 → 核对迁移/兼容/安全代价 → 与既有 finding 去重。仅记录能减少业务或运维成本、且不会削弱隔离、安全、审计、幂等和恢复性的建议；纯个人风格偏好、为了“统一”而统一、或需要大重写却没有明确收益的方案一律剔除。

两轮结束后，将仍成立的真实问题写入 `human-confirmation-checklist.md`，按“一项问题一个确认项”呈现，供人类逐条选择接受、拒绝、延期或补充业务事实。该清单不得提前复制全部 findings，也不得混入未经两轮复核的猜测。

## 6. 持久化产物

- `file-ledger.csv`：逐文件范围、哈希、状态与批次。
- `reading-notes.md`：按批次记录亲读事实与证据。
- `architecture.md`：现状架构与关键时序。
- `data-model.md`：集合、字段、索引、状态和租户键。

- `coverage-report.md`：集合校验、哈希漂移、验证结果与剩余 UNKNOWN。
- `human-confirmation-checklist.md`：100% 覆盖及两轮复审后，留给人类逐项确认的真实业务问题与最小化建议。

## 7. 最终完成门

只有同时满足以下条件才宣称完成：

1. 基线文件与台账集合完全相等。
2. 所有台账行均为 `read_complete` 或 `verified_non_text`。
3. 所有文本源文件均有批次笔记和子系统归属。
4. 关键调用链和集合完成双向反查。
5. 审查期间变化文件均已重读。
6. 最终报告不含未标记猜测。
7. 所有 `UNKNOWN` 明确列出。
8. 阶段 11 已按真实业务闭环完成第一轮循环复审，候选均经过正向、反向、反证与去重核验。
9. 阶段 12 已按业务简化/反过度工程完成第二轮循环复审，并剔除无明确收益的重构偏好。
10. `human-confirmation-checklist.md` 已生成最终待确认项；每项均可回指证据、说明业务影响、给出不过度工程的最小处理选项，并保留人类确认状态。

“100% 阅读”证明审查覆盖完整，不等于无需运行环境即可证明所有外部系统状态。
