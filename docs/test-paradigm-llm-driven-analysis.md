# 测试范式深度分析：从「固定脚本」到「LLM 驱动动态博弈」

> 2026-06-16 动手前深度分析。结论改变整个测试重建工程的重心：之前聚焦「覆盖缺口 + 断言强度」，本分析揭示更根本的天花板——**测试范式本身是"假动态"**。源：深读 `src/prompts.rs`(soul/policy)、`src/agent/decision.rs`+`gateway.rs`(业务流)、`docs/superpowers/specs/2026-06-15-roleplay-fuzz-testing-design.md`、全部 real_llm 多轮测试。

## 一、最根本的发现：现有「多轮」测试全是固定脚本，客户是假的

**所有多轮 LLM 测试的客户台词 100% 写死，无一条 LLM 真的在演客户。**

| 测试 | 客户输入 | 是否反应 agent 上一句 | 证据 |
|---|---|---|---|
| P2 情感陪伴弧 | 固定 4 句数组 | ❌ 预设 | `roleplay_emotional_companion_e2e.rs:583` `let arc=[...]` |
| t15 跌单弧 | 固定 6 句 | ❌ 预设递进 | `real_llm_ops_smoke.rs:2085` |
| t16 千人千面×多轮 | 固定 4 句 | ❌ | `:2197` |
| t17 边界压测 | 固定 5 句横跳 | ❌ | `:2298` |
| t18 暖启动弧 | 固定 4 句 | ❌ | `:2410` |

**博弈链是断的**：客户 t3 说「别一直问」是**预设**的，不是因为 agent t2 真的追问了。agent 无论 t2 说什么，t3 永远那句。roleplay-fuzz 设计里的 LLM roleplayer 是 P3——**全仓库 grep 只命中注释和设计文档，零实现**。

## 二、为什么这是天花板：业务价值恰在动态博弈

业务逻辑分析提炼出这个 agent 最考验能力、最体现价值的 5 个真实场景，**全部依赖客户真实跟随 agent 反应**：

1. **试探 AI 身份 + 嘲讽"模板" + 要真人**：不能复读身份自证（坐实指控）、不能转真人、要靠"只有在场的人才答得出的具体反应"接住。任何固定话术当场露馅——要测的正是"回应是否不可模板化"，固定脚本结构上测不出。
2. **愤怒施压 + 反复要负责人 + 威胁投诉 升级链**：区分"带火气的施压(人还在)"vs"真边界(想离开)"；红线首轮即生效；守边界同时守温度。每多一轮压力都在测"稳不稳"——客户得真的因 agent 的回应升级或软化。
3. **空知识库 + 客户追问价格/案例**：不编造不占位符、只走澄清或承诺核实，又不能哑火。平衡极难，且依赖客户是否接受 agent 的"我去核实"。
4. **情绪未平 + 突然问产品 的模式过桥**：不硬跳销售腔、情绪没平不推进。考验时机感——客户情绪是否真的被上一句接住决定下一句。
5. **翻供自相矛盾 + 比价施压**：跨轮记忆一致性 + 压力下口径稳定 + 标签洁癖协同。需要客户真的制造前后矛盾并对 agent 的应对再施压。

**共性**：情绪轮/压力轮/异议轮 × 自治红线 × 跨轮一致性的**动态叠加**，"正确行为"高度依赖上下文与不可模板化的具体接应。固定脚本只能测"红线字样有没有出现"（如是否冒出"转真人"），**测不出"守红线的方式是否仍有温度、是否仍像真人"**——而后者才是这个 agent 的核心价值。

## 三、三个范式级天花板（按严重度）

**① turn-level judge 测不出累积业务价值（最严重）**
judge 逐轮独立打分（`real_llm_ops_smoke.rs:574`、`emotional_e2e.rs:438`），维度全是"这条像不像真人/有无情绪价值/压不压迫"。**没有 trajectory-level 评估**——没有"4 轮后信任是否提升""N 轮后意向是否推进"。最接近业务结果的只是计数（approved 轮数）。但 agent 的北极星是"经营长期关系、建立信任、自然推进"——这是**轨迹级**目标，turn-level judge 结构上量不到。

**② 客户零真实刁难（范式根因）**
死台词客户不反击 agent 的具体话术。reviewer 校准测试自己的注释坦承：真实 Reply Agent"不会主动产出控制式高压话术"，所以对抗只能靠固定注入。动态刁难（身份探测/诱导越界/情绪反扑真实跟随 agent 失误）**结构上测不到**。

**③ 无跨会话长期关系**
每次全新 testcontainer DB，"不保存跨 run 历史"（设计 §2.6）。t18 暖启动靠手工预置 `agent_profile` 假装老客户，而非真有历史会话沉淀。长期记忆 consolidation(t11) 是孤立单测，没有"客户回来后 agent 记得上次"的端到端弧。

## 四、范式升级方向：「全 LLM 驱动」的真义

用户「全部由 LLM 驱动的测试」诉求 = 范式从「固定脚本断言」升级到：

```
LLM 演客户(动态反应 agent 每句) × 多轮真实博弈 × trajectory 级业务价值评判 × 跨会话长期关系
```

具体三件事：
1. **LLM Roleplayer（演客户）**：给定身份/场景，LLM 扮演客户，**每轮真实反应 agent 上一句**（agent 接得好就软化、接不好就升级刁难）。落地 roleplay-fuzz 设计的 P3。客户只看对话不看 agent 内部（防作弊）。
2. **Trajectory Judge（轨迹裁判）**：评的不是单条回复，是整段对话——"这 N 轮里信任是否累积、意向是否推进、关系是否前进、红线全程是否守住、人设是否一致"。业务结果导向。
3. **跨会话沉淀**：同一客户多次会话间真有记忆/画像/承诺沉淀，测"老客户回来 agent 记得"。

## 五、对 spec 的影响（重心调整）

原 spec（R0-R4 + R2.5）聚焦"覆盖域 + 断言强度 + 全新维度"，仍然必要（地基）。但本分析揭示**最高价值的升级是范式本身**——建议新增贯穿性的：

**R5 · LLM 驱动动态博弈范式（贯穿，最高价值）**
- R5.1 LLM Roleplayer：客户由 LLM 动态扮演，真实反应 agent。
- R5.2 Trajectory Judge：轨迹级业务价值评判（信任/意向/关系推进 + 全程红线 + 人设一致）。
- R5.3 动态对抗：roleplayer 主动试探身份/诱导越界/情绪反扑，跟随 agent 失误升级——测"守红线的方式是否仍像真人"。
- R5.4 跨会话长期关系弧。

R5 是范式重构，R2/R2.5 的跨域+全新维度在 R5 范式下跑（动态客户 × 各域 × 各维度）才能测出真实业务价值，否则仍是"假动态换皮"。

## 六、定位修正（2026-06-16 可行性分析 + 对抗审查后，覆盖上文第五节）

上文第五节把 R5 定位成"贯穿全局、最高价值、取代固定脚本"——经可行性分析与对抗审查，**此定位被修正**。三个核实的硬约束：①seed 不可复现（`llm.rs` 4 处 temperature 硬编码无 seed 通道）②三角色易同源（judge 默认回落 `state.llm`）③成本爆炸（单场景 ~43 次 LLM 调用，进不了 PR 合并门）。

**修正后定位 = 两条并行线，非动态取代固定**：
- **固定回归线**（PR 门，守下限）：确定性业务逻辑（状态机/画像/承诺/记忆/quiet hours）+ 红线硬断言。**t15-18 等现有固定脚本不退役**——动态化确定性逻辑纯属自找 flaky，是减分。
- **动态发现线**（nightly/手动，探能力）：LLM 演客户发现固定脚本测不出的对话质量/抗刁难短板，进 ledger+软门，**不进 PR 门**。
- **连接**：动态发现真短板 → 抽象方法论缺陷 → 修 prompt → 多 seed 变体验证泛化 → 红线契约固化进固定线。

权威定位以 `.kiro/specs/universal-test-coverage/requirements.md` 的「阶段顺序与里程碑」为准。反过拟合四铁律见 [[feedback_dynamic_test_anti_overfitting]]。

**反过拟合守恒**：LLM roleplayer 也要防"客户太配合"或"客户乱演"——roleplayer 有明确人设契约 + 场景目标，judge 评 trajectory 用业务维度（非锁措辞）。[[no-overfitting-methodology]]。
